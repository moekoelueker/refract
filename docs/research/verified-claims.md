### UNVERIFIABLE — Text and links under an Aave-style lens remain not just selectable/clickable but usably targetable — the hit-test offset from visual displacement is negligible.

**Corrected:** Aave claims selectability and clickability but says NOTHING about targeting accuracy, and the underlying mechanism guarantees an offset. Their exact wording is 'The content's own pixels are the ones moving, which is why text under the lens stays selectable and links stay clickable' and 'the content underneath stays selectable, scrollable, and clickable on the same compositor as the rest of the page.' Note what is missing: 'accurately'. CSS `filter` is a paint-time operation; it does not move hit-test geometry, so the pointer target stays at the undisplaced position while the glyphs move by up to 0.5 x scale x mapRange px. This is a genuine latent defect, not a nitpick — a lens is at its strongest displacement exactly at the rim, which is where users aim. WCAG 2.2 SC 2.5.8 Target Size (Minimum) requires 24x24 CSS px; a displacement that shifts a 24px target's apparent centre by >12px makes the visible target and the actual target disjoint, which is a plausible 2.5.8 failure and an unambiguous 3.2.x-style predictability problem. MANDATE: the API must enforce a documented max-displacement budget over interactive regions, or refuse to lens interactive content at all. Ship a lint/dev-mode warning when a lens's bounding box intersects a focusable element.

**Evidence:** https://aave.com/design/building-glass-for-the-web — selectability quotes; no statement about hit-test accuracy, no measurement. https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html (SC 2.5.8, 24x24 CSS px). ### ~~REFUTED~~ — `isolation: isolate` on the glass element reliably fixes both nested-backdrop-filter and border-radius clipping of the backdrop region across Chrome, Safari and Firefox.

**Corrected:** REFUTED as a spec-grounded fix. `isolation` is NOT in the list of backdrop-root-forming conditions. The complete list (MDN, from Filter Effects 2) is: the root element; an element with `filter` other than none; `opacity` less than 1; `mask`, `mask-image`, `mask-border`, or `clip-path` other than none; `backdrop-filter` other than none; `mix-blend-mode` other than normal; and `will-change` set to any of the above. `isolation: isolate` creates a stacking context, which is a different concept, so it has no defined effect on the backdrop root. Any 'fix' it appears to produce is engine-specific happenstance and must not be a blanket rule. THE REAL RULES, which are far more valuable and which the corpus misses: (1) An ancestor with `opacity` < 1 truncates the backdrop root — so ANY entrance/fade animation on an ancestor (Motion/Framer `animate={{opacity:1}}`, a `group-hover:opacity-90`, a 0.999 opacity hack to force a layer) SILENTLY FLATTENS every nested glass surface for the duration of the animation. This is the single most likely 'why is my glass broken' bug in a real app, and it is invisible in static screenshots and static Playwright baselines. (2) `will-change` on ANY of those properties does the same thing permanently — so `will-change: opacity` or `will-change: filter`, both common perf 'optimizations', are glass killers. (3) `clip-path` and `mask` also truncate — so faking squircle corners with `clip-path` on the glass element's ANCESTOR destroys the backdrop. Mitigation: ship a dev-mode runtime check that walks the glass element's ancestor chain and console.warns on any backdrop-root-forming computed style; make it part of the DX story, because nobody else has it.

**Evidence:** https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/backdrop-filter — complete backdrop-root list quoted above; `isolation` absent; 'If a parent element has opacity: 0.9, it becomes a backdrop root and any child's backdrop-filter will only blur content between that parent and the child — not the content behind the parent. This is a common source of confusion.' Spec: https://drafts.fxtf.org/filter-effects-2/#BackdropRoot. No primary Chromium/WebKit bug or WPT test supports the `isolation` remedy; the claim's own sources were secondary (w3tutorials, search snippets).

### PARTLY TRUE — A View Transitions snapshot rasterises the element, so a live `backdrop-filter` under a transition may freeze or stop updating mid-transition.

**Corrected:** Half right, and the half that is right is the visible half. Per CSS View Transitions Level 1: `::view-transition-old()` is 'a static visual capture of the old state' while `::view-transition-new()` is 'a live capture of the new state'. So the outgoing glass IS frozen and the incoming glass IS live — which means a morphing glass pill cross-fades a frozen blur into a live blur. On a scrolling photo backdrop that reads as a visible ghost/tear at exactly the marquee moment, which is worse than a uniform freeze because it looks like a bug rather than a stylistic choice. Two further hazards the corpus misses: (a) the spec applies `filter` and `opacity` 'when generating its image' for the old snapshot — and `opacity` on a group pseudo is a backdrop-root-forming condition, so the default group-anim opacity crossfade can flatten a nested glass surface for the duration of the transition; (b) the view-transition pseudo tree lives in the top layer, so a `backdrop-filter` inside a `::view-transition-new` capture samples the transition tree, not the page. RECOMMENDATION INVERTED, as the claim anticipated: give the glass a `view-transition-name` on its FRAME/geometry only, set `view-transition-class` to disable the default old/new crossfade for glass surfaces, and let the material re-render live rather than being captured. Add a real 60fps recording of this to the test suite — it is a one-frame artifact that no screenshot test will catch.

**Evidence:** https://drafts.csswg.org/css-view-transitions-1/ — '::view-transition-old() ... a static visual capture of the old state'; '::view-transition-new() ... a live capture of the new state'; §1.5 Rendering Model: 'properties like filter or opacity ... are applied when generating its image', mix-blend-mode 'can't be applied to its image' and is applied to ::view-transition-group(). Backdrop-root interaction follows from https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/backdrop-filter (opacity < 1 forms a backdrop root).

### Checklist

## MUST-NOT-GET-WRONG CHECKLIST — performance, accessibility, shipping reality

Ordered by (probability it bites you) x (damage when it does). Items 1-4 are launch-blocking.

---

### 1. Never claim a contrast guarantee you cannot compute. Build the oracle on sampled pixels or don't ship the feature.
**Why this is #1:** the contrast story is your headline differentiator, and the mechanism the plan proposes for it does not work.

- [ ] Delete `contrast-color()` from the ContrastText design. It returns **only `white` or `black`** ("A `<named-color>` of either `white` or `black`"), it takes a **declared color value** — it cannot see composited pixels, and a glass surface has no declared effective background. MDN itself warns it fails on mid-tones: `#2277d3` → black text, "not readable for small text."
- [ ] Accept that **WCAG 2.2 gives you no methodology here.** SC 1.4.3's Understanding doc says to evaluate "the foreground and background colors obtained from the user agent, or the underlying markup and stylesheets, rather than the text as presented on screen." For glass, the stylesheet background is `rgba(255,255,255,.2)` — not what the user sees. There is no defined conformance path for a composited variable backdrop. Say this out loud in your docs; it is the single most credible thing you can write.
- [ ] Implement the oracle as **runtime backdrop luminance sampling**: downsample the backdrop region, compute per-tile luminance, take the **worst-case tile under the text bounding box** (not the mean — the mean is how you ship a nav bar that's fine over the dark third of a hero and illegible over the sky), and drive tint alpha / scrim opacity from that. Budget for this being client-only and RSC-hostile. Price it in now.
- [ ] Enforce **WCAG 2.x ratio** as the gate; make **APCA advisory only**. This is not a taste call, it is a licensing call — see item 11.
- [ ] Provide a **guaranteed-legible escape hatch** as a first-class API, not a footnote: an opaque content plate behind text (`ContentPlate`, or `plate` prop) that is on by default for body copy. Every practitioner mitigation converges here; Apple's own guidance is a dimming layer.
- [ ] Ship **one contrast test that runs in CI**: render each component over a fixed set of adversarial backdrops (white, black, mid-tone `#2277d3`, high-frequency noise, a photo with a bright/dark split under the text), sample the composited pixels, assert ≥4.5:1 for body and ≥3:1 for large/UI. Fail the build. This is the test nobody else in the category has.
- [ ] Numbers you may cite: 4.5:1 body / 3:1 large (18pt or 14pt bold ≈ 24px / 18.5px). Numbers you may **not** cite: "1.5:1" (Infinum's own words, "We clocked 1.5:1 in places," zero methodology), "~50% blur reduction," "40%→60% opacity floor" (AI-generated publication, see item 12).

### 2. Ship a persisted, in-product transparency control. Do not build accessibility on `prefers-reduced-transparency`.
**Why:** the media query is undetectable in Safari and Apple has an *unresolved privacy objection* to it, not a backlog item.

- [ ] `prefers-reduced-transparency` support, verified 2026-07-24: Baseline **limited**; Chrome/Edge **119** only; **Safari `version_added: false`** (WPT stable+experimental score 0); **Firefox 113 is behind the pref `layout.css.prefers-reduced-transparency.enabled`** and WPT-scores 0 — do **not** list Firefox as supported anywhere in your docs. Chrome usage is **0.048%** of page loads.
- [ ] Read the blocker: WebKit standards-position #145 is still **"Needs position"** with label **`concerns: privacy`** and the note about "a potential fingerprinting risk," open since 2023-03-13. WebKit bug 175497 has been NEW and unassigned since **2017-08-11**, with a community PR (#11560, 2023-03-15) unmerged for 3+ years. **Plan for this to never ship in Safari.**
- [ ] Therefore: the primary mechanism is a **provider prop + persisted user preference + `data-*` attribute on the root**, with the media query as progressive enhancement. Layer in `prefers-contrast: more` and `forced-colors: active` as additional signals.
- [ ] Copy Apple's own web precedent for the reduced tier, because it is measured and citable: on apple.com, tint alpha rises from **`.8` → `.92`** (light) and **`.8` → `.88`** (dark) when `--globalnav-backdrop-filter` is `none`. A real shipped fallback ratio beats an invented one.
- [ ] Verify the control works with **VoiceOver + Safari** and in **forced-colors mode**, and that the toggle is discoverable in-product (Access Advisors' specific critique of Apple was that the control is buried in Accessibility settings).

### 3. Guard the backdrop root. This is the bug that will make your library look broken in other people's apps.
**Why:** it is invisible in screenshots, invisible in Storybook, and triggered by the most ordinary code in a React app.

- [ ] Memorize the actual list. An element forms a backdrop root — truncating every nested `backdrop-filter` — if it is the root element, or has `filter` ≠ none, **`opacity` < 1**, `mask`/`mask-image`/`mask-border`/**`clip-path`** ≠ none, `backdrop-filter` ≠ none, `mix-blend-mode` ≠ normal, or **`will-change` set to any of those**. `isolation` is **NOT** on this list — the blanket `isolation: isolate` rule in the companion CSS is cargo cult, has no spec basis, and must not be a global default.
- [ ] The three real killers, all common: (a) **any ancestor fade-in animation** (`animate={{opacity:1}}`, `group-hover:opacity-90`, the `opacity:.999` layer-promotion hack) silently flattens the glass for the duration; (b) **`will-change: opacity` or `will-change: filter`** on an ancestor kills it permanently — and both are things people add *for performance*; (c) **faking squircle corners with `clip-path`** on the glass or its ancestor destroys the backdrop.
- [ ] Build the **dev-mode ancestor walker**: on mount in development, walk up from each glass element, read computed styles, and `console.warn` naming the offending ancestor and property. ~40 lines. This is a headline DX feature and no competitor has it — lead with it.
- [ ] Add a **computed-style assertion in CI** ("no ancestor of a glass element forms a backdrop root") — this catches the class of bug that pixel-diffing locks in rather than catches.
- [ ] Always render glass as a block / inline-block / `flow-root` box, never a bare fragmentable inline. The "Chrome doesn't do inline backdrop-filter" claim is unverified, but the mitigation is free.

### 4. Detect capability by rendering, never by `CSS.supports` and never by UA string.
- [ ] `CSS.supports('backdrop-filter','url(#x)')` returns **true in Safari and Firefox** because the value parses. Using it selects the broken tier. Every library in the corpus gets this wrong.
- [ ] Do **not** copy samasante's `/^((?!chrome|chromium|android).)*safari/i.test(navigator.userAgent)`. And do not copy its `useIsWebKit` shape either: it initialises `false` and flips in an effect, so in Safari **every** glass surface renders wrong once then re-renders — a guaranteed hydration flash plus an avoidable render pass per instance.
- [ ] Probe once, synchronously-ish, at module scope: render a known displacement into a tiny offscreen surface, read it back, cache the result, expose it as a `data-glass-tier` attribute on the root so CSS can branch without JS per component. SSR-render the **safe** tier and upgrade, never the reverse.
- [ ] Firefox specifics: `backdrop-filter: url(#f) blur(12px)` drops the **entire declaration** (Bugzilla 1961378, NEW). So the material must be **stacked independent layers** — a tint/blur layer that survives when the url() layer doesn't — not one declaration.
- [ ] Do not bet the architecture on Safari shipping SVG backdrops. The PRs (#68613, #68614, #69566) are all **OPEN**, none merged, #68614 is **`merging-blocked` with no reviewer**, bug 245510 is still **NEW/unassigned**. And even if it lands, the author's own known-limitations list says **"backdrop animations only update when the element repaints"** — a Safari native backdrop will not update while content scrolls behind a static glass bar. Treat copy-mode / `filter: url()` as a **permanent** first-class path.

### 5. Derive your own performance budget. There is no citable number in this field.
- [ ] Do not repeat: HyperFrames' **200ms** (no device, no GPU, no tool, no methodology — "illustrative"), Cygnis' **"1-2 blur layers per screen"** (native-blur heuristic, irrelevant to CSS/SVG cost), studiomeyer's **15-30% FPS drop** (no methodology), or **"keep blur radii under 20px."**
- [ ] Know that the radius folklore is probably **inverted**. liquid-dom's cost model shows mip-pyramid separable blur cost *falling* with radius and converging to ~**2.667 A**: a 17-tap kernel costs **18.000 A at L0** (≤8px) but **2.727 A at L4** (~48-64px). The real cost drivers are **area × number of independent render surfaces**, not radius. State your budget in those terms.
- [ ] Publish the first reproducible benchmark in the category. Committed scene, digest-pinned browser builds, named devices. Report **p95 frame time and long-animation-frame count during a scripted scroll**, not average FPS. Sweep surfaces {1,2,4,8} × area {nav bar, card, full sheet} × radius {8,16,24,40} × DPR {1,2,3}, on ≥ a Pixel-6a-class Android, an A13/A14-class iPhone, and an integrated-GPU laptop, in Chrome + Safari + Firefox. Report the delta with the effect off. Attach the traces.
- [ ] Do not assert "Safari runs SVG filters on the CPU." WebKit PR #68613 is about a **CoreImage-backed** input and #68614 touches the **accelerated filter path** — both mean GPU. And the one cross-engine datapoint in the corpus runs the *other* way: Bugzilla 1718471 comments report Firefox "faster than Chrome," and shadcn #327 reports Chromium "heavily affected" while Firefox is not. Measure, don't theorize.
- [ ] Respect the two limits the corpus does agree on: displacement lenses **bloom into an oval when stretched across a wide dock-style bar** (use frost-only for full-width chrome, reserve the lens for content-sized elements), and WebKit has a **source-graphic size ceiling** past which it **silently drops the costlier passes** (chroma + specular) while the base bend survives — so cap `filterResolution` at 1× on WebKit and add a test that asserts the specular pass actually rendered.
- [ ] Cap chromatic aberration. Three displacement passes triples filter cost for an effect most users can't see below 2× DPR.

### 6. Do not put UI inside a canvas. If you use a shader tier at all, it is a decorative overlay only.
Every one of these is documented, not speculative:
- [ ] **No live backdrop exists.** HTML-in-Canvas has **not shipped** — WICG explainer says "not yet shipped," behind `chrome://flags/#canvas-draw-element`, API `drawElementImage()`. A chromestatus API search finds no feature entry, no origin trial, no milestone; "Canvas Formatted Text" is "No longer pursuing." Every shader glass library therefore refracts a **stale html2canvas snapshot** — liquidGL literally depends on `html2canvas@^1.4.1`.
- [ ] **Text is permanently blurrier.** "Subpixel text anti-aliasing" is explicitly *excluded* from `drawElementImage()` output as sensitive information. That is the exact "looks cheap" tell you're trying to avoid.
- [ ] **Hit testing, IntersectionObserver and accessibility all read DOM location, not drawn location** — the explainer's own words. You must maintain a shadow geometry model; any divergence is an invisible a11y and pointer bug.
- [ ] **Canvas a11y requires a parallel tree.** HTML spec: authors "**must** also provide content that … conveys essentially the same function or purpose as the canvas element's bitmap," and "Authors **should** have a one-to-one mapping of interactive regions to focusable areas in the fallback content." Maintaining that duplicate tree is the maintenance disaster.
- [ ] Also broken by a canvas tier and worth enumerating honestly in your docs: text selection, native find-in-page (Cmd-F), browser zoom and text-only zoom, print, tab focus order, `prefers-reduced-motion`, translation extensions, mobile GPU memory, and battery.
- [ ] Overlapping glass fails in the dominant WebGL material: drei's MeshTransmissionMaterial samples `uniform sampler2D buffer` — an FBO of the scene rendered with the parent discarded — so it has no notion of a second transmissive surface. Glass-sheet-over-glass-toolbar is a core UI pattern; this is a stronger argument against the WebGL tier than bundle size.
- [ ] The live proof: liquid-dom has **2,403 stars** and requires **both** `navigator.gpu` **and** a Chrome flag. Enormous demand, zero shippability.

### 7. Transition the frame, not the material.
- [ ] Per View Transitions L1, `::view-transition-old()` is "a static visual capture of the old state" while `::view-transition-new()` is "a live capture." So a morphing glass pill **cross-fades a frozen blur into a live blur** — over a scrolling backdrop that reads as a tear at exactly your marquee moment.
- [ ] Also: the spec applies `filter` and `opacity` "when generating its image," and `opacity` < 1 is a backdrop-root condition — so the default group crossfade can flatten nested glass mid-transition. And the pseudo tree lives in the top layer, so a `backdrop-filter` inside a captured `::view-transition-new` samples the transition tree, not the page.
- [ ] Mitigation: put `view-transition-name` on the **frame/geometry only**, disable the default old/new crossfade for glass surfaces via `view-transition-class`, and let the material re-render live.
- [ ] Test this with a **real 60fps recording**, not a screenshot. It is a one-frame artifact and no snapshot test will catch it.

### 8. Fix the animation baseline before tuning a single spring value.
- [ ] Motion's real `springDefaults` (motion 12.42.2, read from source): **`stiffness: 100`** (not 1), `damping: 10`, `mass: 1.0`, `duration: 800`, **`bounce: 0.3`** (not 0.25), `visualDuration: 0.3`.
- [ ] Precedence is the **opposite** of what the plan assumes: physics defaults apply first and are only replaced if you passed duration/bounce **and** no physics keys (`if (!isSpringType(options, physicsKeys) && isSpringType(options, durationKeys))`). So bare `{type:'spring'}` = ζ **0.5**, ω 10 rad/s (~0.63s period) — a slow, bouncy baseline. Every "Apple-like" recommendation in the plan is offset from the wrong zero. Re-derive them all.
- [ ] The SwiftUI conversion arithmetic does check out: response 0.55 / ζ 0.825 → k ≈ 130.5, c ≈ 18.85, m = 1. Use explicit `stiffness`/`damping`/`mass`, never rely on the default.
- [ ] Apple's own shipped web motion tokens, verified: easing `cubic-bezier(.4,0,.6,1)` (78 uses vs 13 for the runner-up), durations **.24s** (58) and **.32s** (26). Ship those as `--ease-standard` / `--duration-2` / `--duration-3`.
- [ ] Honor `prefers-reduced-motion` for *specular sweeps and morphs*, not just for translation — a moving highlight on a glass surface is motion.

### 9. Test the two failure modes screenshots cannot see; don't over-invest in pixel diffing.
- [ ] Blur output **is** driver-dependent — Firefox before 123 disabled the property entirely on "systems with unknown GPU vendor" (bug 1868737). So digest-pin the Playwright Docker image and the browser build, force SwiftShader/`--disable-gpu` for determinism, and set a non-zero `maxDiffPixelRatio`.
- [ ] But treat glass snapshots as **change detection only**. The two bugs that will actually hurt you are invisible to pixel diffing: a flattened backdrop root produces a *plausible* screenshot (and if the baseline was captured broken, the test locks the bug in), and a frozen view-transition capture is a one-frame artifact.
- [ ] The tests that assert correctness are the ones from items 1, 3 and 7: sampled-pixel contrast assertion, ancestor backdrop-root assertion, 60fps transition recording.
- [ ] Chromatic vs self-hosted is now a cost question, not a correctness one.

- [ ] The tsdown `unbundle` directive-preservation claim is **unverified** and the failure is silent and catastrophic — a stripped `'use client'` means a hard render error for every Next.js App Router consumer, and it will not appear in your unit tests or Storybook.
- [ ] CI gate (~30 lines): after every build, assert each source file containing `'use client'` still has it as the **first statement** of the emitted file (after any `"use strict"`); assert it is **absent** from every emitted `.d.ts`; then `npm pack` → install into a real App Router fixture → `next build`. This makes the bundler choice reversible.
- [ ] Build on **`@base-ui/react`** (1.6.0, MIT, 2026-06-18, 81 export subpaths) — not `@base-ui-components/react`, whose `latest` is frozen at `1.0.0-rc.0` (2025-12-04). shadcn's 2026-07-02 changelog: "Starting today, Base UI is the default component library in shadcn/ui." - [ ] Depend on neither `class-variance-authority` (frozen at 0.7.1 since 2024-11-26, registry `time.modified` identical) nor `cva` (`latest` is a 0.0.0 placeholder, only `beta: 1.0.0-beta.8`). - [ ] Style queries are usable for nesting (Baseline newly 2026-05-19, Firefox 151) but WPT stable is uneven — Safari **0.556**, Firefox 0.778, **firefox_android 0**. ### 13. Squircles: use exponent 4, and never `clip-path`.
- [ ] Spec verbatim: "we'll write it as 2^K: x^(2^K) + y^(2^K) = 1. The K in this equation is the `superellipse()` argument … setting K to 1 gives the standard circle/ellipse equation … the traditional 'squircle' uses a K of 2." The spec even warns that "most literature … will write the equation with a simpler x^K exponent." So `squircle` = **exponent 4**. A naive exponent-K SVG fallback renders a plain ellipse and *looks* implemented.
- [ ] `corner-shape` is **Chrome 139+ only** (Firefox `false`, Safari `false`, experimental) — pure `@supports` enhancement. The `border-radius` fallback must look correct standalone, which constrains your radius scale.
- [ ] **Never** fake squircles with `clip-path` — it forms a backdrop root and destroys the glass (item 3).

CORRECTED GUIDANCE: (a) never put `view-transition-name` on a glass element or any ancestor — name a sibling 'frame' element; (b) prefer scoped/element transitions when glass is on screen; (c) expect a frozen backdrop during root transitions and cap them at ~300 ms. **Evidence:** https://drafts.csswg.org/css-view-transitions-1/ §2.1.1 (backdrop root quote), §7.1.3 / §7.3.1 / §7.9 (old backdrop-filter captured; backdrop-filter written into group keyframes and group styles rule; new element content = 'capturing the image'). https://api.webstatus.dev/v1/features?q=id:view-transitions → newly 2025-10-14; chrome 111, safari 18, firefox 144.

## Browser-support checklist — glass on the web, 2026-07-24

### A. THE ARCHITECTURAL VERDICT (read this first)

- [ ] **Do NOT build a "Safari flips to native `backdrop-filter: url()`" strategy.** WebKit bug 245510 is NEW/unassigned since 2022-09-22. The three PRs (#68613, #68614, #69566) are from a first-time community contributor (`Iskz17`, 3 lifetime WebKit PRs); #68614 is labelled `merging-blocked` with zero reviews; Apple's compositing owner commented "This looks AI-generated" on 2026-07-16, and the author replied "Yeah, AI helped with this one". **Copy-mode / `filter: url()` is a permanent first-class architecture, not a shim** — give it a real API surface (`refract`, `behind`) and budget for it indefinitely.
- [ ] **Invert the framing:** the cross-engine technique is `filter: url(#svg)` on the wrapped subtree (Blink + WebKit + Gecko, today). Blink-only is refracting an *arbitrary backdrop*. Say it that way — it is both true and better positioning.
- [ ] **Never ship `backdrop-filter: url(#f) blur(12px) saturate(180%)` as one declaration.** Gecko bug 1961378 ("backdrop-filter gets *ignored* if it would fall back to a blob image") makes whole-declaration drop plausible. Use two stacked layers: a frost layer (`backdrop-filter: blur() saturate()`, all engines) + a separately-mounted refraction layer (Blink only).
- [ ] **Prefer `data:` URLs over `blob:` for the `feImage` href.** samasante's shipping code uses `data:image/svg+xml;charset=utf-8,…`; `blob:` is exactly what triggers Gecko's blob-image fallback named in bug 1961378. Keep the map same-origin so `feDisplacementMap`'s `in2` is never tainted — Filter Effects 1's taint restriction is why Gecko bug 1808785 was closed INVALID.
- [ ] **Never put `view-transition-name` on a glass element or any ancestor of one.** Per CSS View Transitions L1 §2.1.1, an element whose `view-transition-name` is not none **"at any time"** *forms a backdrop root* — permanently. Name a sibling frame element instead.

### B. SAFE TO SHIP AS DEFAULT (no fallback needed)

- [ ] `filter: url(#svgFilter)` with `feImage` + `feDisplacementMap` on HTML content — all three engines.
- [ ] `backdrop-filter` with filter *functions* — Baseline newly 2024-09-16 (Chrome 76 / Edge 79 / Firefox 103 / Safari 18; `-webkit-` for Safari 9–17).
- [ ] `@media (prefers-contrast: more)` — Safari 14.1+, Chrome 96+, Firefox 101+, non-experimental. **This is your primary a11y query on Apple platforms.**

### D. EXACT FEATURE-DETECTION SNIPPETS

**D1 — `backdrop-filter: url()` (the one with no real feature query).**
```js
// CSS.supports('backdrop-filter','url(#x)') === true in Safari AND Firefox
// (url() is legal <filter-value-list> grammar per Filter Effects 2), so it
// CANNOT be used. There is no CSS/JS query for whether it RENDERS.
// Use a Blink-only capability as the proxy: Houdini paintWorklet has shipped
// only in Chrome 65+/Edge 79+ and in no other engine since 2018.
export const canRefractBackdrop =
  typeof CSS !== 'undefined' &&
  'paintWorklet' in CSS &&                          // Blink only
  CSS.supports('backdrop-filter', 'blur(1px)');
// MUST be user-overridable, and MUST be revisited if WebKit PR #68614 merges.
```

**D2 — reduced transparency (works around Safari's total absence).**
```js
// An UNKNOWN media feature parses to 'not all' — that is the support probe.
const mq = matchMedia('(prefers-reduced-transparency: reduce)');
export const queryIsSupported = mq.media !== 'not all';   // false: Safari, default Firefox
export const reduceGlass =
  userPreference ??                                        // your persisted toggle wins
  (queryIsSupported && mq.matches) ||
  matchMedia('(prefers-contrast: more)').matches ||        // Safari 14.1+ / FF 101+ / Cr 96+
  matchMedia('(forced-colors: active)').matches;
```

**D3 — squircle corners.**
```js
export const hasCornerShape = CSS.supports('corner-shape', 'squircle');
```

  .glass { corner-shape: squircle; }            /* == superellipse(2) == exponent 4 */
}
```

```

### E. NAMING — the trademark risk is real but narrow

The risk is concentrated in exactly one use: the mark as **your product's name**.

**Evidence that it is narrow.** "Liquid Glass" is **not** on Apple's official trademark list (only `Liquid Retina®` and `Liquid Retina XDR®`; compare `Aqua® | user interface`, `Dynamic Island®`, `SF Symbols®`). Apple's WWDC25 press release calls it "a new material called Liquid Glass" with **no ™/® symbol** and no trademark footer. npm has **3,907** packages matching "liquid glass"; `@callstack/liquid-glass` — a named commercial consultancy — ships **82,862 weekly downloads** under that exact name, unchallenged since 2025-09. Apple's GitHub DMCA record (2023–2026, every notice enumerated) targets **only verbatim Apple code and docs**: `apps.apple.com` source/assets, the Apple Books production JS bundle 6.600.298, and the Apple-documentation repo. A code search of `github/dmca` for "Apple liquid glass" returns **0**. GitHub's standard is "clear intent to mislead"; npm defers to it and "does not resolve squatting claims on demand."

**Evidence that it is real.** Apple's trademark list states: *"The absence of a product or service name or logo from this list does not constitute a waiver of Apple's trademark or other intellectual property rights concerning that name or logo."* US rights arise from use in commerce, and Apple has used the term continuously since 2025-06-09 (25× in the press release, 41× on the HIG Materials page, and in Icon Composer's Design Resources copy). Apple's third-party guidelines are explicit and are **about names**: *"a. The Apple word mark is **not part of the product name**. b. The Apple word mark is used in a referential phrase such as 'runs on,' 'for use with,' 'for,' or 'compatible with.' c. The Apple word mark appears **less prominent** than the product name. … e. The reference to Apple does not create a sense of endorsement, sponsorship, or false association."* Plus: *"The goodwill derived from using any part of an Apple trademark exclusively inures to the benefit of and belongs to Apple."*

- [ ] **DO NOT** name the library, npm package, GitHub repo, or docs domain `liquid-glass*`, `liquidglass*`, or `*-liquid-glass`. (Also: the bare npm name `liquid-glass` is already taken — 1.0.0, 2025-06-09, ISC.)
- [ ] **DO** pick a distinctive coined mark you can own, and use Apple's term **only** in the referential tagline: e.g. **`glassify` — "Apple-style Liquid Glass for the web."** Your mark must be visually more prominent than "Liquid Glass" in the README hero, the docs header, and the OG image.
- [ ] **DO** keep the npm `description` referential; **DO** remove `"apple"` from npm `keywords` *(`@samasante/liquid-glass` ships `"apple"` as a keyword — don't)*; keep `liquid-glass`, `glassmorphism`, `refraction`, `feDisplacementMap` as descriptive keywords.
- [ ] **NEVER** use the Apple logo or any Apple-owned graphic symbol; never put an Apple wordmark in your logo, favicon, or social card; never use Apple UI screenshots, device bezels, or Apple wallpapers in demos.
- [ ] **NEVER** write "pixel-perfect recreation of Apple's iOS 26 Liquid Glass" *(that is `nikdelvin`'s framing, and it carries no disclaimer — the highest-exposure posture in the corpus)*. Say "inspired by", "in the spirit of", "an independent take on".
- [ ] Realistic worst case for a descriptive user is a rename request, not litigation — so keep the coined mark load-bearing and the Apple term detachable. If you ever have to drop it, nothing breaks.
- [ ] Register your coined mark early (domain + npm scope + GitHub org) so a rename is never forced from the other direction.

**Disclaimer placement, real precedents.** Best in class is `XingAur/cool-ui`'s "Independence notice" — it names the companies, names the marks, **and** asserts no-asset-redistribution, the three things a reviewer checks. `samasante/liquid-glass` pairs technique attribution with non-affiliation in one paragraph. `iplanwebsites/solid-glass` and `ethbak/icon-composer-mcp` carry one-liners. Negative controls with **no disclaimer at all**: `rdev/liquid-glass-react` (5,704★), `nikdelvin/liquid-glass`, `deepika-builds/liquid-glass`, `kostyniuk/glasscn-components`.
